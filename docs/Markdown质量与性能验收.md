# Markdown 质量与性能验收

日期：2026-09-19。第五阶段进行中；已完成下述质量检查、跨段源码格式操作和多入链性能修复，并加入整篇正文源码编辑与大文档批量格式化优化。竞品使用同一工作流的完整应用实测尚未完成。

## 首批质量改进（提交 5df2995）

- 行内公式的闭合符每个解析状态只建立一次索引，避免未闭合 `$x ` 长段落反复扫描剩余全文。保留价格、转义、空白、代码和公式分隔符的原有规则。
- 重复标题的地址生成、标题身份匹配使用计数与分组查找。删除无法区分的同名标题时，仍产生明确失效目标，不误跳到其他章节。
- 链接位置来自解析器成功识别的语法。覆盖表格单元格、转义竖线、引用定义、未引用脚注、嵌套脚注、提示块标题、任务列表、CRLF／CR／LF 和 Unicode；避免全局地址匹配误改文字。
- 数据库版本 16 带安全副本重建旧来源索引，已存在但此前漏收集的表格链接无需重新编辑即可参与改名维护。
- 普通编辑行不再因其他段落的解析结果更新而重复刷新；表格和高级预览继续接收整篇文档的定义、脚注和任务状态。
- 大写字母、Caps Lock 形式的撤销／重做／查找快捷键保持一致；组合输入期间继续由输入法处理候选内容。

## 固定性能语料

运行 `npm run benchmark:markdown`。语料在 `tests/fixtures/markdown-quality.ts`，报告输出到 `test-results/markdown-quality-report.json`，包含硬件、运行时、输入 SHA-256、源代码指纹、原始耗时和回归上限。CI 单独运行该基准并上传报告。

固定场景包括 800／4000 块混合文档、1000 行表格、单段 2000 张图片、4000 个重复标题、15000 字符未闭合公式、12000 个未闭合方括号及 2000 层引用输入。每项预热 2 次、测量 7 次；该小样本的 p95 就是最大值。上限用于发现明显性能退化，不是交互延迟承诺。

本机对照使用 Windows x64、i7-9750H、约 47.88 GiB 内存、Electron 的 Node 22.16.0。旧版本来自 `git archive ce7b8aa` 的独立目录，并复制同一个基准脚本与固定语料；共用相同依赖、相同采样方式。

| 场景 | 旧版本中位数 | 本轮中位数 |
| --- | ---: | ---: |
| 未闭合公式导入，15000 字符 | 1400.53 ms | 4.74 ms |
| 4000 个重复标题解析 | 1409.14 ms | 55.36 ms |
| 4000 个重复标题身份维护 | 1505.13 ms | 11.14 ms |
| 混合 4000 块来源链接提取 | 270.03 ms | 234.75 ms |

原始记录见 [旧版本](benchmarks/markdown-quality-before.json) 和 [本轮版本](benchmarks/markdown-quality-after.json)。候选版本报告中的 `commit` 是运行时工作区基点，`workingTreeChanged` 和源代码指纹用于区分本轮未提交的代码；远端 CI 报告以实际受测提交为准。一般场景的小幅差异可能来自系统噪声，不据此宣称整体加速。

## 实际输入与语言

- Electron 测试在 642 块文档中依次输入中文、日文、韩文、表情与未闭合公式，确认自动保存和阅读内容。
- 从 Chromium 的可信 `input` 事件记录到第二次 `requestAnimationFrame`，经过一次渲染机会。该数据是输入到画面的近似指标，不是操作系统实际屏幕呈现时间；测试启动参数关闭 GPU。
- 报告包含 15 个原始样本、中位数及 p95，输出 `test-results/markdown-input-frame-report.json`，CI 上传留档。独立复现：`npx playwright test e2e-tests/long-document-experience.spec.ts --grep "next rendered frame"`，此前需运行 `npm run build`。
- 本轮完整 Electron 验收中的中位数为 73.20 ms、p95 为 132.10 ms，见 [原始输入帧记录](benchmarks/markdown-input-frame.json)。这是单台机器上固定文档的结果，不能推断所有文档规模或设备的表现。
- 可设置 `KNOWBOOK_PROFILE_MARKDOWN=1` 生成 Chromium CPU profile。分析模式有额外开销，与未开启分析的结果分别记录。
- 输入法测试使用 Chromium CDP 的候选输入、提交和取消路径，覆盖中文候选、日文／韩文／阿拉伯文和组合表情的保留，以及格式化、撤销重做、重载。它不是 Windows 系统输入法候选窗口的人工验收。

## 跨段格式与关系一致性

- 在同一个源码编辑区中跨空行选中内容时，粗体、斜体、删除线、高亮和行内代码按解析出的行内区域分别处理。保留标题、列表、任务、引用、提示块与脚注的结构；整块代码和公式保持原文。
- 混合已有样式和普通文字的多段选区先统一添加样式，再次操作统一移除。支持 LF／CRLF／CR、中文与 Emoji；移除行内代码标记保留原始换行。跨段链接创建独立链接，选中首个地址。
- 块视图仍使用独立编辑区；新增“编辑 Markdown 源码”提供完整正文的连续文字选区。按原生输入前选区和格式操作事务追踪来源，应用时保留仍存在内容的块 ID、标签与高亮，并重建嵌套关系；应用可整体撤销。固定语料覆盖跨两个独立段落的部分选区、保存和文件往返。
- 出链、入链和自动维护共用解析后的来源索引。代码、公式和图片替代文字中的 Wiki 字面文本不计入文档关系；只切换块类型也刷新关系。Wiki 保留大小写不敏感的路径／唯一标题解析，目标后创建、改名和跨文档块引用均有回归。
- 数据库版本 17 先保留迁移安全副本，再重建旧关系及搜索索引。搜索行 ID 使用独立的整数主键映射，更新不再按全文索引的未索引字段扫描全表；不依赖可能被数据库整理改变的原表隐含行号。迁移、删除、行号复用、VACUUM、回滚、移动和重启均检查搜索结果与索引完整性。实现依据见 [SQLite FTS5](https://www.sqlite.org/fts5.html) 和 [VACUUM 的行号行为](https://www.sqlite.org/lang_vacuum.html)。

## 整篇源码编辑与批量格式化

固定语料在 `tests/fixtures/markdown-source-performance.ts`，分别为 800 块（101769 字符）和 4000 块（512089 字符），包含标题、中文／英文段落、代码围栏和标签。`npm run benchmark:markdown-source` 分别测量打开源码、输入、全文加粗和应用；预热 2 次、采样 7 次，逐次核对块 ID、标签及代码字面内容。块结构核对在计时之外，格式化还包含一次源码结果一致性比较。报告包含输入摘要、源码指纹与运行环境，CI 独立执行并上传。

旧版本使用 `git archive bd50148` 的独立源码副本及同一个基准脚本和语料。在 Windows x64、i7-9750H 的本机对照中，全文格式化由逐段重建全文、逐段遍历块位置，改为收集互不重叠的修改后一次拼接正文、批量映射块位置。随机边界编辑、重复段落、空块和跨段格式回归同时比较批量与逐次操作的身份语义。

| 全文加粗计算 | `bd50148` 中位数 | 优化后中位数 |
| --- | ---: | ---: |
| 800 块 | 1173.50 ms | 21.86 ms |
| 4000 块 | 26332.34 ms | 109.68 ms |

原始记录：[旧版本](benchmarks/markdown-source-before.json)、[优化后](benchmarks/markdown-source-after.json)。这部分是独立进程的计算耗时，不包含窗口渲染，也不是竞品速度对照。

实际 Electron 验收在两种规模下打开源码弹窗，在首部／中部／尾部输入中文、日文、韩文和 Emoji，再执行全文加粗、撤销／重做、应用、保存和重载。每次操作从可信输入事件计时至第二次动画帧，提供一次渲染机会；GPU 由测试环境关闭。格式化预热 2 次、采样 7 次，输入采样 15 次；打开和应用各记录一次，只作为当前机器的观测值。

| 实际源码界面 | 800 块 | 4000 块 |
| --- | ---: | ---: |
| 打开（单次） | 581.30 ms | 1585.20 ms |
| 输入中位数／p95 | 20.90／40.20 ms | 84.40／142.10 ms |
| 全文加粗中位数／p95 | 116.50／148.90 ms | 581.00／688.70 ms |
| 应用（单次） | 690.10 ms | 2986.10 ms |

原始记录：[800 块](benchmarks/markdown-source-frame-800.json)、[4000 块](benchmarks/markdown-source-frame-4000.json)。两种规模均通过保存、重载以及全部原始块 ID、标签和代码字面内容断言。打开与应用在大文档中仍为秒级，不能以格式化计算的 110 ms 代替完整界面的延迟。

性能门槛用于发现明显退化：打开 3000 ms、输入 500 ms、全文格式化 1500 ms、应用 8000 ms。测试定位限定在菜单和弹窗中，避免测试框架在几千个无关控件上计算名称的额外开销。不可将这些门槛解释为产品交互目标或操作系统实际呈现延迟。报告和截图由 CI 的 `markdown-source-report` 留档。

提交 `bbc2816` 的 [CI](https://github.com/zhenhua32/knowbook/actions/runs/35441919713) 中，Windows 验收通过；Linux 的 4000 块全文格式化 p95 在三次执行中为 1.58～1.60 秒，超过 1.5 秒门槛，另观察到一次连续格式切换的选区异常。本轮保持原有门槛：源码编辑框保留稳定的初始值，由原生输入更新正文，只在格式化及历史恢复时写入文本；在同步布局阶段恢复选区，避免下一次快捷键使用尚未恢复的位置。源码等宽编辑区单独设置绘制方式和布局隔离，块编辑器也同步恢复格式选区。

上表已更新为这次修复后的完整 Markdown 回归记录，测量时关闭了竞品测试进程。报告的源码指纹包含源码编辑区 CSS；字体和渲染环境会影响结果，不以不同运行间的小幅差异宣称加速。预算失败时，在计时样本之外另存一次渲染追踪；本地可用 `KNOWBOOK_PROFILE_MARKDOWN_FORMAT=1` 采集格式化 CPU profile，分析结果不得混入正常性能样本。

## 热门目标与存储基准

运行 `npm run benchmark:markdown-links`。通过真实存储接口创建 100／1000 个入链来源，每个来源 20 个块，另有 2000 个无关文档；完成全部派生索引后再测量。章节改名影响其中 10% 的来源，文档改名影响全部来源。预热 2 次、采样 7 次，更新计时之外逐个检查来源内容、关系、断链和返回的受影响文档集合。

旧版本来自 `git archive 5df2995` 的独立源码目录。使用相同的生成语料、操作、采样与断言；报告包含环境、源码指纹、原始样本和回归上限。源码指纹是脚本列出的文件集合，最终提交验证以远端 CI 的受测提交为准。

| 1000 个来源、2000 个无关文档 | 旧版本中位数 | 本轮中位数 |
| --- | ---: | ---: |
| 修改目标正文 | 10.96 ms | 2.27 ms |
| 修改一个章节标题 | 2855.72 ms | 260.95 ms |
| 文档改名并维护全部入链 | 13303.63 ms | 3573.57 ms |

原始记录：[旧版本](benchmarks/markdown-links-before.json)、[本轮版本](benchmarks/markdown-links-after.json)。改进来自按章节筛选来源、复用事务内索引，以及消除全文搜索更新中的全表扫描。文档改名仍需实际写入所有变化来源；千来源场景仍为秒级操作，不能将结果表述为所有编辑均无延迟。

Linux CI 独立执行这 6 项存储基准并上传报告。正文／章节／整篇改名的中位数回归上限分别为 250／1500／10000 ms；它们用于发现明显退化，不是界面交互延迟承诺。
