# ADR-0006：动态插件采用工作区优先、立即激活模型

- 状态：Implemented
- 日期：2026-08-29
- 取代：ADR-0005 中“会话预览插件→另行安装到工作区”的动态插件流程

## 背景

旧流程把 AI 创建的插件定义为 `session-preview`，只有创建它的助手会话能够查看、预览和激活。实际对话中，模型可能新建会话、恢复旧会话或先调用工作区安装工具，结果是插件记录已经存在，但后续工具得到“not visible in this assistant session”或“owning assistant session”错误。多次恢复还会耗尽 12 step 上限，最终没有任何插件运行。

这个所有权边界没有帮助用户完成插件任务，反而把“定义存在”“revision 存在”“运行可见”拆成了互相冲突的状态。

## 决策

动态插件改为单一的工作区生命周期：

1. AI 新建的插件定义从一开始就是 `workspace`。
2. `plugins.list`、`inspect`、`preview_revision` 和诊断对当前工作区的全部定义可见，不再按助手会话过滤。
3. 历史 `session-preview` 定义在首次列出、查看、编辑或工作区激活时原地升级为 `workspace`；保留 `createdSessionId` 作为来源记录，不再把它当作访问控制条件。
4. `plugins.activate_revision` 直接在工作区作用域启动精确 revision，并在同一工具调用中返回真实成功或失败结果，不再暂停等待另一轮批准。
5. `plugins.install_workspace` 只作为旧会话的兼容别名保留；新流程不再需要“预览后安装”的第二次操作。
6. stop 和 rollback 也操作工作区运行，保证不同助手会话看到同一个插件事实。
7. agent 单轮预算由 12 步提高到 64 步，允许完整检查、生成、验证、运行和修复；运行失败仍必须反馈给模型，不能伪装成功。

## 保留边界

本决策放开的是会话所有权、重复安装和人工批准限制。QuickJS/WASM 隔离、capability broker、不可变 revision、静态校验和原子激活继续保留，因为它们同时提供稳定 API、失败诊断和热更新回滚能力，不是导致插件不可运行的会话流程限制。

## 结果

- 创建插件后即可在设置页、首页卡片等工作区 UI 插槽中持续使用。
- 新对话可以继续修改或修复旧对话创建的插件。
- 激活错误在当前 turn 内回到模型，模型有足够步数生成新 revision 并重试。
- 旧数据库不需要离线迁移；访问旧预览定义时会自动升级。
